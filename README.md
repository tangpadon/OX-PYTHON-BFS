# เอกสารอธิบายการทำงานของระบบเกม OX (Tic-Tac-Toe BFS)

เอกสารนี้จัดทำขึ้นเพื่ออธิบายโครงสร้าง สถาปัตยกรรมเชิงวัตถุ (OOP) และขั้นตอนวิธี (Algorithms) ของระบบเกม OX (Tic-Tac-Toe) ขนาด 3×3 ขับเคลื่อนด้วยไฟล์หลัก [`main.py`](main.py) เพียงไฟล์เดียว ครบถ้วนทั้ง **แกนประมวลผล BFS Game Tree**, **อัลกอริทึม Minimax**, **ระบบแสดงผล Debug Console** และ **หน้าต่างกราฟิก (Tkinter GUI)** โดยพัฒนาด้วยไลบรารีมาตรฐานของ Python ทั้งหมด (Zero External Dependencies)

## 2. คำอธิบายรายละเอียดแต่ละคลาส (Detailed Class Breakdown)

### คลาส `OXBoard` (การจัดการกฎและกระดาน)
ทำหน้าที่รวบรวมกฎและฟังก์ชันการจัดการกระดานเกม 3×3 ไว้ในที่เดียว โดยกระดานถูกแทนค่าด้วยสตริงความยาว 9 ตัวอักษร เช่น `'         '` (กระดานว่าง):

* `WINNING_COMBOS`: ทูเพิลเก็บดัชนีชุดเส้นชัยชนะ 8 เส้นทาง (แนวนอน 3, แนวตั้ง 3, ทะแยงมุม 2)
* `get_opponent(player)`: สลับสัญลักษณ์ผู้เล่นระหว่าง `'X'` และ `'O'`
* `swap_symbols(board)`: สลับตัวอักษร X เป็น O และ O เป็น X ทั่วทั้งกระดาน สำหรับการเทียบเคียงสถานะสมมาตร
* `place_symbol(board, position, player)`: คืนค่าสตริงกระดานสถานะใหม่เมื่อมีการลงสัญลักษณ์ในตำแหน่งที่ระบุ
* `check_winner(board)`: ตรวจสอบสถานะกระดานว่ามีฝ่ายชนะหรือไม่ หรือเกมเสมอกระดานเต็ม (`'Draw'`)

### คลาส `OXDebugger` (ระบบบันทึกและจัดรูปแบบการค้นหา)
ทำหน้าที่แปลงข้อมูลสถานะและกิ่งก้านของ Game Tree ให้เป็นข้อความเชิงเทคนิค (Algorithmic Debug Output) โดยตัดข้อความสนับสนุนการตัดสินใจ (DSS) ออก เพื่อมุ่งเน้นข้อมูลโครงสร้างต้นไม้เกมอย่างแท้จริง:

* `format_row(board, start_index)`: จัดรูปแบบการแสดงผลกระดานแถวละ 3 ช่องให้อ่านง่าย เช่น `X | . | O` ผ่าน List Comprehension
* `get_debug_text(tree, board, player, turn, chosen_move)`:
  * แสดงภาพจำลองกระดานปัจจุบันในเทิร์นนั้น
  * แจกแจงกิ่งลูกที่เป็นไปได้ทั้งหมด (Child Nodes) เรียงลำดับตามความสำคัญของกลยุทธ์ (Minimax ➔ Steps)
  * แสดงค่าประเมิน **Minimax Value** (`+1`, `0`, `-1`) โดยหากเป็นกิ่งที่ชนะจะระบุจำนวนตาเดินที่ปิดเกมเร็วที่สุด เช่น `+1 (ชนะใน 1 ตา)` หรือ `+1 (ชนะใน 3 ตา)`
  * แสดงภาพจำลอง (Preview) ของกระดานเมื่อเดินในแต่ละช่อง
  * ระบุกิ่งที่ AI ตัดสินใจเลือกเดิน (`AI เลือกเดิน: ช่อง (...)`)

### คลาส `GameNode` และ `OXBFSTree` (แกนประมวลผลต้นไม้เกม BFS Engine)
หัวใจหลักของการค้นหาและการตัดสินใจของ AI ประกอบด้วย 2 คลาสหลัก:

#### 1) คลาส `GameNode` (โครงสร้างโหนดต้นไม้เกม)
เก็บข้อมูลสถานะของแต่ละโหนดใน Game Tree:
* `board`: สตริงสถานะตาราง ณ โหนดนั้น
* `player_turn`: ผู้เล่นที่มีสิทธิ์เดินในตานี้
* `move`: ดัชนีช่อง (0–8) ที่เดินมาจากโหนดแม่
* `children`: ลิสต์เก็บโหนดลูกที่เป็นไปได้ทั้งหมด
* `is_terminal`: บูลีนระบุว่าเป็นจุดสิ้นสุดเกมแล้วหรือไม่
* `wins_x`, `wins_o`, `draws`: สถิติจำนวนเส้นทางจบเกมที่เป็นไปได้ใต้กิ่งนี้
* `minimax_val`: ค่าประเมินกลยุทธ์ตามหลัก Minimax
* `steps_to_end`: จำนวนก้าวเดินที่เกมจะจบลงใต้กิ่งนี้ (ใช้คำนวณ Fastest Win / Delay Defeat)

#### 2) คลาส `OXBFSTree` (อัลกอริทึมสร้างและประเมินต้นไม้)
* **การสร้างต้นไม้ด้วย BFS (`_build_tree`)**:
  * ใช้ **Queue (FIFO)** ผ่าน `collections.deque`
  * เริ่มต้นที่ Root (`' ' * 9`, ตาของ X) แล้วขยายกิ่งทีละชั้นตามแนวกว้าง (Level-by-Level)
  * ครอบคลุมสถานะเกมที่เป็นไปได้ทั้งหมดจำนวน **549,946 โหนด** และมีโหนดปลายทาง (Leaves) **255,168 โหนด**
  
* **การส่งต่อค่า Minimax และนับผลลัพธ์แบบย้อนกลับ (Bottom-Up Backpropagation)**:
  * ใช้ `for node in reversed(all_nodes):` คิดย้อนจากโหนดใบ (Leaves) กลับขึ้นไปหาราก (Root)
  * **โหนดใบ (Terminal):** กำหนดค่าตามผลลัพธ์จริง ($X ชนะ = +1, O ชนะ = -1, เสมอ = 0$) และ `steps_to_end = 0`
  * **โหนดแม่:** 
    * บวกสะสมจำนวนครั้ง ชนะ/แพ้/เสมอ จากลูกทุกกิ่ง (`node.wins_x += c.wins_x`, ...)
    * ตาของ X (Maximizer) $\rightarrow$ ดึงค่าลูกแล้วหา $\max$
    * ตาของ O (Minimizer) $\rightarrow$ ดึงค่าลูกแล้วหา $\min$
    * **การคำนวณจำนวนตาเดิน (`steps_to_end`)**:
      * หากตาเดินนั้นนำไปสู่ **ชัยชนะ**: เลือกกิ่งลูกที่ชนะเร็วที่สุด $\min(\text{steps}) + 1$
      * หากตาเดินนั้นนำไปสู่ **ความพ่ายแพ้**: เลือกกิ่งลูกที่ยื้อเกมนานที่สุด $\max(\text{steps}) + 1$
      * หากตาเดินนั้นนำไปสู่ **การเสมอ**: เลือกกิ่งลูก $\min(\text{steps}) + 1$

* **การประเมินและเลือกตาเดิน (`evaluate_branches`)**:
  AI ทำการเลือกตาเดินผ่านอัลกอริทึม Minimax และขั้นตอนวิธีนับก้าวที่กระชับและสมบูรณ์ในตัวเอง (Pure Game-Theoretic Decision) เพียง 2 ด่าน โดยไม่ต้องพึ่งพา Hard-coded Heuristics:
  1. **Minimax Filtering (การันตีผลลัพธ์ตามทฤษฎีเกม):**
     * กรองเฉพาะกิ่งที่ให้ค่า Minimax สูงที่สุดจากมุมมองของตนเอง (`best_m = max(b['minimax_val'])`)
  2. **Fastest Win / Delay Defeat (เลือกกิ่งที่ชนะเร็วที่สุด / ยื้อเกมให้นานที่สุด):**
     * **กรณีการันตีชนะ (`best_m == +1`):** เลือกกิ่งที่ใช้จำนวนก้าวเดินน้อยที่สุดเพื่อปิดเกมให้เร็วที่สุด ($\min(\text{steps})$) โดยหากมีช่องชนะทันที ($\text{steps} = 1$) จะถูกเลือกเป็นอันดับแรกโดยอัตโนมัติ
     * **กรณีการันตีแพ้ (`best_m == -1`):** เลือกกิ่งที่ยื้อเกมให้นานที่สุด ($\max(\text{steps})$) ซึ่งจะบังคับให้บล็อกตาชนะของคู่แข่งโดยอัตโนมัติ และเปิดโอกาสให้คู่แข่งเดินพลาด
     * **กรณีเสมอ (`best_m == 0`):** เลือกกิ่งแรกในกลุ่มที่การันตีเสมอ (`best_candidates[0]['move']`)

## 3. ทฤษฎีและขั้นตอนวิธี: ความสัมพันธ์ระหว่าง BFS และ Minimax

โปรเจกต์นี้ทำงานแบบ **Hybrid Algorithm** โดยผสานจุดเด่นของทั้ง 2 อัลกอริทึม:

```
[ เริ่มต้น ]
    │
    ▼
[ 1. BFS Phase ] (แนวกว้าง Level-by-Level)
ขยายสถานะกระดานด้วย Queue (FIFO)
ครอบคลุม 549,946 โหนด และ 255,168 Leaves
    │
    ▼
[ 2. Minimax Phase ] (คิดย้อนกลับ Bottom-Up)
ส่งต่อค่า {+1, 0, -1} จาก Leaves ขึ้นสู่ Root ผ่าน min() / max()
พร้อมสะสมสถิติเส้นทาง (Wins, Losses, Draws)
    │
    ▼
[ 3. Decision Phase ]
AI เลือกเดิน: Best Minimax (+1 > 0 > -1) ➔ Fastest Win / Delay Defeat
```

### คำถามพบบ่อยเกี่ยวกับ Minimax ในโปรเจกต์นี้:

#### 1) ทำไมค่า Minimax ที่คิดย้อนกลับจึงคงค่าแค่ `+1`, `0`, `-1` ในทุกระดับ?
เพราะ Minimax เป็นการ **"เลือกค่าที่ดีที่สุดเพียงค่าเดียว (Selection via `min()` / `max()`)"** ไม่ใช่การ "บวกเลขสะสม (Summation)"
* ผู้เล่นไม่สามารถเดินทุกกิ่งพร้อมกันได้ แต่ต้องเลือกเดินเพียงตาเดียวที่ดีที่สุด
* เมื่อโหนดใบเริ่มต้นที่ค่า $\{-1, 0, +1\}$ การหา $\max$ หรือ $\min$ ของเซตนี้ย่อมได้ผลลัพธ์กลับมาเป็นสมาชิกในเซตเดิมเสมอ
* ตัวเลขเหล่านี้คือ **สถานะการันตีผลลัพธ์ (Guaranteed Outcome)**: `+1` = ชนะแน่นอน, `0` = เสมอแน่นอน, `-1` = แพ้แน่นอนหากคู่แข่งเล่นดีที่สุด

#### 2) ถ้ามีสถิติ ชนะ / แพ้ แล้ว ทำไม AI ถึงต้องเชื่อค่า Minimax เป็นหลัก?
* **สถิติ ชนะ / แพ้:** เป็นการนับเส้นทางเกมทั้งหมดแบบสุ่ม (รวมถึงตาที่คู่ต่อสู้เดินพลาดด้วย)
* **Minimax:** คำนวณภายใต้สมมติฐานว่า **"คู่แข่งเล่นเก่งที่สุด (Optimal Opponent)"**
* หากกิ่งหนึ่งมีสถิติชนะ 99 ทาง แต่มีหลุมพรางให้แพ้ 1 ทาง ซึ่งคู่แข่งมองเห็นได้ง่าย สถิติจะดูน่าเดิน (99 ต่อ 1) แต่ Minimax จะเตือนว่ากิ่งนี้คือ `-1` (แพ้แน่นอน)
* **การผสานงาน:** AI จึงใช้ Minimax เป็นตัวกรองความปลอดภัยด่านแรก (ป้องกันการเดินเข้าตาแพ้) แล้วใช้สถิติ ชนะ/แพ้ เป็นตัวตัดสินกรณีที่ค่า Minimax เท่ากัน (Tie-breaker)

## 4. สรุปการปรับปรุงโค้ดให้กระชับและมีประสิทธิภาพ (Optimizations)

โค้ดได้รับการตรวจสอบและปรับลดความซ้ำซ้อนตามหลัก Clean Code:

| จุดที่ปรับปรุง | ก่อนปรับปรุง | หลังปรับปรุง | ประโยชน์ที่ได้รับ |
| :--- | :--- | :--- | :--- |
| **เกณฑ์การตัดสินใจ (Decision-Making)** | ใช้เกณฑ์ 4 ด่าน (มี Hardcoded Block และ Score Heuristic) | ตัดเหลือ **2 ด่านแท้จริง (Best Minimax ➔ Fastest Win / Delay Defeat)** | ตัดโค้ดเงื่อนไขยุทธวิธีซ้ำซ้อน ใช้พลังคำนวณของ Minimax และ Game Tree 100% |
| **พารามิเตอร์ `depth` ใน `GameNode`** | เก็บ `self.depth` และส่งต่อ `node.depth + 1` | ตัด `depth` ออก | ลด Memory Overhead ในการสร้าง Object กว่า 5.4 แสนโหนด |
| **เมธอด `get_debug_text` ใน `OXBFSTree`** | สร้างคลาส `OXDebugger()` ซ้ำซ้อนใน Tree | ให้ GUI เรียก `self.debugger` โดยตรง | ลดความผูกมัด (Decoupling) ระหว่าง Engine และ Formatter |
| **การสลับผู้เล่นใน `OXGameGUI`** | เขียนบล็อก `if-else` ตรวจสอบ `'X'` และ `'O'` | เรียก `OXBoard.get_opponent()` | นำฟังก์ชันเดิมกลับมาใช้ซ้ำ (Code Reuse) |
| **ฟังก์ชัน `format_row`** | ใช้ลูป `for` และสร้าง list ว่าง 6 บรรทัด | ใช้ List Comprehension 2 บรรทัด | โค้ดกระชับ อ่านง่าย และประมวลผลเร็วขึ้น |
| **มาตรฐานการจัดช่องว่าง** | ช่องไฟไม่สม่ำเสมอ | เว้น 2 บรรทัดระหว่างคลาส, 1 บรรทัดระหว่างฟังก์ชัน | สอดคล้องตามมาตรฐาน PEP 8 สากล |
